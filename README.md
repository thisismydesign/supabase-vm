# supabase-vm

Self-hosted Supabase, one VM per project, on a VPS. The VM is the boundary: whatever happens on the host (tool installs, Docker restarts, agents) does not reach it.

- **VM** — incus on the host, Ubuntu image, fixed CPU, memory and disk, autostart.
- **Supabase** — the official self-hosting bundle inside the VM, keys generated by its own scripts, Docker publishing on localhost only.
- **Access** — a proxy inside the VM forwards to the API on localhost. No port is opened on the host. Two options:

| Access       | Tailscale (no domain needed)                                    | Own domain                                                      |
| ------------ | --------------------------------------------------------------- | --------------------------------------------------------------- |
| Public API   | Funnel at `https://<vm>.<tailnet>.ts.net`                       | Cloudflare Tunnel at `https://<host>.<domain>`                  |
| Studio       | Same URL, dashboard password                                    | Same URL, behind Cloudflare Access                              |
| Deploy       | Tailscale GitHub Action joins CI to the tailnet; Postgres 5432  | Postgres as a TCP service behind Access; CI opens it by token   |
| SSH          | `ssh ubuntu@<vm>` over Tailscale                                | `incus exec <vm> -- bash` on the host                           |
| Depends on   | Tailscale relays and account; disable key expiry per device    | Cloudflare and the domain                                       |

Tailscale is what the scripts set up today. Swap to the domain once it exists: install cloudflared in the VM, route the hostname to `localhost:8000`, set `SUPABASE_PUBLIC_URL` and `API_EXTERNAL_URL` in `.env`.

## Host, once

```sh
git clone https://github.com/thisismydesign/supabase-vm ~/workspace/thisismydesign/supabase-vm
```

`host/create-vm.sh` installs incus and the firewall rules on first use.

## Per project

```sh
host/create-vm.sh supabase-<project> https://<frontend-url>   # creates the VM and starts the stack
# approve the printed Tailscale login URL, then:
incus exec supabase-<project> -- /opt/supabase-vm/expose.sh      # Funnel for the API, tailnet TCP for Postgres
```

Keys and passwords live in `/opt/supabase/.env` inside the VM. Keep a copy as `.env.supabase-<project>` in this checkout; it is gitignored.

## Deploying a project to it

From GitHub Actions, in the project's deploy job, after joining the tailnet with `tailscale/github-action` (OAuth client tagged `tag:ci`):

```sh
supabase db push --db-url "$SUPABASE_DB_URL"        # postgresql://postgres.<tenant>:<password>@<vm>.<tailnet>.ts.net:5432/postgres
rsync -a --delete --exclude main --exclude deno.jsonc supabase/functions/ ubuntu@<vm>.<tailnet>.ts.net:/opt/supabase/volumes/functions/
ssh ubuntu@<vm>.<tailnet>.ts.net 'cd /opt/supabase && docker compose restart functions'
```

`create-vm.sh` generates the SSH key on the host as `~/.ssh/<vm>-ci` and authorises it for `ubuntu` in the VM; its private half is a repo secret. The frontend gets `SUPABASE_URL=https://<vm>.<tailnet>.ts.net` and `SUPABASE_PUBLISHABLE_KEY` from `.env`.

Manual fallback from the host: `host/deploy-functions.sh <vm> supabase/functions`, and `db push` against the same URL.

## Footprint

Defaults: 4 vCPU, 4 GiB, 30 GiB, settable per VM on `create-vm.sh`. Measured on supabase-stash, idle, 2026-10-31:

| Resource | Use                                                                                  |
| -------- | ------------------------------------------------------------------------------------ |
| CPU      | Load ≈ 0.5 of 4 cores                                                                |
| Memory   | ≈ 1 GiB for the containers, ≈ 1.7 GiB for all guest processes; the host sees the full limit once the guest's page cache fills it, and it does not shrink |
| Disk     | 13 GiB on the host after install, 10 GB of it Docker images. The disk is sparse, so the limit is a cap, not a cost; it must fit two image sets during an upgrade. It cannot be shrunk later |

Memory is a hard cap: the guest drops cache, then kills a container, and the host is never affected. Change it live with `incus config set <vm> limits.memory=4GiB`.

## Operate

| Task       | Command                                                                      |
| ---------- | ---------------------------------------------------------------------------- |
| Shell      | `incus exec supabase-<project> -- bash` on the host, or `ssh ubuntu@supabase-<project>` over Tailscale |
| Studio     | `https://supabase-<project>.<tailnet>.ts.net`, dashboard user and password from `.env`  |
| Snapshot   | `incus snapshot create supabase-<project> before-<change>`                   |
| Roll back  | `incus snapshot restore supabase-<project> before-<change>`                  |
| Upgrade    | `incus exec supabase-<project> -- bash -c 'cd /opt/supabase && sh update.sh && docker image prune -af'` |
| Logs       | `incus exec supabase-<project> -- docker compose -f /opt/supabase/docker-compose.yml logs -f` |
